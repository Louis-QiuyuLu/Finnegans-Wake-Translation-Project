# 同步与发布

## 合入前

确认目标仓库、分支、用户已有授权及当前远端版本。用户已经要求持续翻译并同步自有仓库时，沿原授权执行，不把参考项目每次重新确认的做法带入。需要新权限、改仓库可见性或另设发布目标时，先把具体结果准备好，再说明所需决定。

对照本批底本包、初译、审校和研究采用记录。核公共章稿仍保留正确原文、初译和真实状态。研究资料只有摘要时，不能在合入说明写「已核全文」；没有人工审校时，不写「人工复核完成」。

## 检查差异

同时看已跟踪和新增文件。检查四类内容：

1. 章稿：段落 ID、页行、顺序、原文、译文、注释来源、异译与审校状态。
2. 资料：来源用途与实际查阅相符；术语只合入采用的增量；工作包与报告可追溯。
3. 进度：断点不越过缺口，上下文与公共稿一致，生成稿包含本批。
4. 发布：不含凭据、整书缓存、临时下载和 `dist/`；没有夹带他人未授权改动。

运行根规则所列检查与构建。只改文档或技能无需新增镜像实现的测试；仍须核路径、链接和可执行示例。改网页逻辑才另跑相应 Node 测试。通过后无需反复扩大测试范围，除非有新修改或未解失败。

## 远端有变更

先读取最新提交与差异，再合并，不盲目重试旧快照。逐字段处理同段冲突：原文用底本证据决定；译文保留双方异译；来源表按稳定 ID 去重；术语冲突回维护阶段；断点依据实际连续稿重新核，不能简单取较大坐标。

远端改变了本批原文、术语或采用稿时，旧审校不覆盖新输入。列差异交回相应角色，不能靠重算指纹或复写文件使报告看似有效。

使用 GitHub 连接器写 Git 对象时，尽量基于刚读取的远端树更新实际改动路径。若必须上传完整快照，先确认本地基线与远端一致，完整保留远端文件、权限和其他修改。提交的父节点必须是刚核过的提交；更新引用绑定 `expected_sha`。拒绝后重新读取并合并，不改成强推。

连接器、Git CLI 或其他工具能力不足时可以换可用方式。不要为了同步重新生成 SSH 密钥或索取用户凭据；已有授权不等于可以查看私钥。没有写入能力便准确报告未上传，保留可复查成果。

## 验证远端与网页

上传成功后核远端提交和关键文件，再查 CI／Pages。提交成功、检查通过、部署成功和页面已更新分别陈述，不能互相代替。

页面核本批段落锚点、译注及下一断点；只修技能时核对应文件和目录链接。构建失败先保留已提交稿，查失败范围；修复后再部署，不删除有效译稿来掩盖失败。

网页缓存仍旧时检查部署所用提交，必要时重取页面。不要因为 Pages URL 返回 200 就宣称包含最新译文。

## 版本与交付说明

提交说明先写问题与改后行为，再列范围、底本和验证。单段译注可用「译注 I.1 004.01–004.17」；技能架构修改说明新增角色、关口与研究能力。AI 模型、用量、费用和用时没有日志便不填估算成事实。

有发布标签时说明收录范围、试译状态、已知未决问题和读本链接。日常续译不必每批创建新版本，也不把标签当作全书完成证明。交付用户时提供实际提交、可用读本和下一起点；未上线便写部署状态。
